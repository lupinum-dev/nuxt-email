# Nuxt Email v1.0 readiness

This is the release gate for `@lupinum/nuxt-email` 1.0. The `1.0.0-beta.2` contract is feature-frozen. This record states what must remain true and which evidence is still required before stable publication. Command output, tarball sizes, and hashes belong in the release artifact manifest rather than values copied into this document.

## Product contract

Nuxt Email is a typed, Nitro-native transactional email renderer for Nuxt. Its v1 value is the combination of:

- ordinary Vue SFC templates under `app/emails/`;
- generated, per-template `renderEmail(name, props)` types in Nitro;
- eighteen built-in server-rendered email primitives plus opt-in `ECodeBlock`;
- email-safe Tailwind v4 through `ETailwind`;
- one isolated Vue SSR renderer shared by Nitro, preview, and testing;
- deterministic `{ html, text, subject? }` output;
- a development-only `/__email` preview backed by typed sibling fixtures; and
- behavior-by-behavior conformance evidence against the pinned React Email oracle.

The package is intentionally for transactional email inside a Nuxt application. Maizzle remains the recommended alternative for standalone email projects, static or marketing builds, non-Nuxt stacks, and configurable transformation pipelines.

## Competitive decision

Continue the project and publish v1 after the recorded gates pass. Adjacent Vue email renderers validate the demand, but they do not make this package redundant. Nuxt Email's defensible product is not merely a Vue port of React Email components; it is the complete Nuxt application workflow around them:

- recursive SFC discovery with generated per-template name and prop types;
- a Nitro-only `renderEmail` call with no parallel registry or sidecar renderer;
- Tailwind v4 compiled into email-safe inline styles and residual head rules;
- one renderer shared by production, preview, and test utilities;
- explicit public entry points with preserved runtime error identity;
- case-by-case React Email oracle evidence and deterministic output; and
- verified exclusion of templates, rendering dependencies, fixtures, and preview routes from the client and production surfaces where they do not belong.

`nuxt-email-renderer` is in the same product family and carries substantial Vue Email component/rendering DNA into Nuxt. Do not claim that React-Email-style Vue primitives or server rendering are unique. Its current string-name rendering API does not couple a discovered template name to that SFC's props, its open typed-rendering work still does not provide that mapping, and it has no Tailwind implementation or versioned React Email oracle. Position the **generated name/props contract + Tailwind v4 + verified stable output** combination.

Tailwind v4 should lead the launch message because it is a visible, requested capability and a real gap in adjacent Nuxt tooling. It is the acquisition hook, not the whole moat. The durable promise is **typed transactional email that belongs to the Nuxt app**. Do not claim that email templates automatically inherit browser CSS variables or the Nuxt application's compiled stylesheet; applications must pass concrete tokens into `ETailwind` from their canonical token source.

Maizzle is a close technical relative in v6, including Vue SFCs and Tailwind v4, but serves a different product boundary. It now has an official `@maizzle/nuxt` integration, so do not claim that Nuxt presence alone is unique: the module connects Maizzle's preview/static-build workflow to Nuxt, while its request-time `render()` remains path/raw-SFC based and untyped. Nuxt Email's distinction is generated typed request-time Nitro rendering with one application registry and output path. Recommend Maizzle openly for standalone, static, marketing, and transformation-heavy workflows. Competing on breadth would turn Nuxt Email into a less mature Maizzle and weaken the zero-configuration Nitro contract.

## Public surface

The npm identity is `@lupinum/nuxt-email`. The unscoped package is unrelated.

| Entry point | Contract |
| --- | --- |
| `@lupinum/nuxt-email` | Nuxt module with one optional `codeBlock` configuration; type-only `RenderedEmail` and `EmailComponentProps` helpers. |
| `@lupinum/nuxt-email/define-email` | Explicit template metadata API and its metadata errors. |
| `@lupinum/nuxt-email/testing` | Typed standalone component renderer, `RenderedEmail`, and `EmailRenderError`. |
| `@lupinum/nuxt-email/errors` | Supported runtime error classes. |

`renderEmail` is generated as a Nitro server auto-import. It is not a package export and must not enter client code.

## Supported environment

- Node.js `^22.18.0 || ^24.11.0 || ^26.0.0`; CI covers Node 22, 24, and 26.
- Nuxt `>=4.5.1 <5`; Nuxt `4.5.1` is the compatibility baseline.
- Vue `^3.5.35`.

The release consumer installs and builds with Nuxt `4.5.2` without a dependency shim.

Nuxt 3, Nuxt 5, edge runtimes, and client-side rendering are outside v1.

## Automated release gate

The beta candidate and final release commit must each pass, from a clean checkout with the repository-pinned pnpm:

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm test:types
pnpm test
pnpm oracle:check
pnpm conformance:check
pnpm performance:measure
pnpm dev:build
pnpm release:verify
```

The release verifier must build the exact tarball, inspect its package metadata and public subpaths, install it into isolated default and code-block-enabled consumers at the exact supported Nuxt baseline, type-check, production-build, and render twice byte-identically. Production-boundary tests must prove that templates and the renderer remain server-only and that preview routes and fixture modules are absent from production. Candidate Nuxt versions outside the peer range are tested separately before the range is widened.

CI must run lint, types, and tests across its supported operating-system and Node matrix. Oracle, conformance, documentation, package, and fresh-install jobs must be required rather than advisory before the beta or v1 tag. The authoritative beta candidate is the `nuxt-email-release` artifact produced by successful `main` CI; its manifest must identify the exact clean commit, version, `next` channel, and tarball hashes.

## Pending stable-release gate

Automation and real-application installation do not prove visual equality in Gmail, Apple Mail, Outlook, or every other client. These items are deliberately pending for `1.0.0-beta.2` and must be complete before stable `1.0.0` publication:

1. Generate the committed proof fixture as HTML, plain text, and `.eml`.
2. Inspect the delivered message in Gmail web, Apple Mail, and Outlook for Windows, including dark-mode behavior where the client supports it.
3. Complete [the client QA checklist](./client-qa-checklist.md) and [the manual QA record](../testing/manual-email-client-qa.md) with client versions, screenshots, defects, and a final decision.
4. Complete at least one [external transactional beta](../testing/external-beta.md) using the exact candidate tarball.
5. Verify that the public documentation site matches the package contract and deploy it.
6. Record owner approval of the remaining documented limitations.

The preview's HTML byte count is exact, but its Gmail clipping warning is only an approximate authoring budget. The preview has no dark-mode simulation; real-client inspection is the authority.

## Deliberately outside v1

- provider adapters, sending endpoints, recipient management, and provider-neutral delivery APIs;
- additional module options, configurable discovery paths, and a public registry protocol;
- raw-HTML primitives or unsafe-content escape hatches;
- a Maizzle-style CLI, static campaign build, or general transformation pipeline;
- automatic inheritance of the Nuxt application stylesheet or browser CSS variables;
- a dark-client simulator or claims of pixel-identical rendering across clients; and
- edge-runtime and client-side email rendering.

For shared design tokens, applications should pass a concrete Tailwind v4 `theme` string or `config` to `ETailwind`, sourced from their own canonical token module. Nuxt Email does not add a second CSS discovery path.

## Feature freeze and roadmap

Do not add features after `1.0.0-beta.2` and before stable v1. Accept only defects, documentation corrections, and required dependency compatibility work. A necessary breaking API change produces another beta. The next work is evidence gathering and defect repair, not breadth. Post-v1 ideas and rejected directions are recorded in the [future roadmap](../roadmap.md).

## Positioning and launch

Use one category sentence everywhere:

> Typed transactional email for Nuxt, with email-safe Tailwind v4.

The launch demo should show a single continuous workflow: create `app/emails/welcome.vue`, use ordinary typed props and `ETailwind`, inspect the exact HTML/text/subject in `/__email`, then call `renderEmail('welcome', props)` from Nitro. Lead with the generated call-site type error and the rendered Tailwind output; those demonstrate value faster than a component inventory.

Use three proof points beneath the headline:

1. **Nuxt-native and typed:** discovered SFC names and props become the Nitro API.
2. **Tailwind v4 made email-safe:** compatible declarations are inlined and responsive/pseudo rules are preserved in the head, with documented client limits.
3. **One verified output path:** preview, tests, and production share the renderer; conformance and determinism are published as evidence.

Publish an honest comparison page rather than a winner-takes-all matrix. Say that `nuxt-email-renderer` is the broader Vue Email continuation for Nuxt, with DevTools, i18n, layers, and module options, while Nuxt Email is the narrower deterministic compiler with a typed Nitro registry, Tailwind v4, oracle evidence, and strict production boundaries. Say that Maizzle is stronger for standalone and marketing workflows. Never market "Vue instead of React" as the differentiator and never imply pixel parity across inbox clients.

The launch package should include the scoped npm release, deployed documentation, a short screen recording, one technical announcement explaining the architecture and tradeoffs, the React Email migration guide, and a Maizzle comparison/boundary note. Distribution should focus on Nuxt channels and real examples from transactional applications rather than component-count claims.

Success for v1 is modest and measurable: the exact candidate works in at least one external Nuxt application, the documented first-email path succeeds without maintainer intervention, no P0/P1 client defect remains from the Gmail/Apple Mail/Outlook proof set, and early issue reports confirm or correct the intended boundary. npm downloads and stars are secondary; time-to-first-render, defect quality, and repeat use are the useful signals.

## Publication decision

The owner may publish the CI-certified `1.0.0-beta.2` artifact with npm tag `next` after the three-client smoke test. Publish stable `1.0.0` only when the automated gate passes on the final clean commit, the full eight-client light/dark checklist and external beta are recorded, no known P0/P1 defect remains, and the accepted limitations match this document. A required breaking change produces another beta.
