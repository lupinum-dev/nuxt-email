## Frozen v0.1 contract

The authoring surface is the E-prefixed Nuxt auto-components `EHtml`, `EHead`, `EBody`, `EPreview`, `EContainer`, `ESection`, `ERow`, `EColumn`, `EHeading`, `EText`, `ELink`, `EImg`, `EHr`, and `EButton`. Templates are ordinary Vue SFCs using Vue props, attributes, slots, `defineProps()`, `v-if`, and `v-for`.

The only application rendering API is the generated, server-only `renderEmail(name, props)`. Template names and props come from recursive `app/emails/` discovery, and success returns exactly `{ html, text }`. There is no provider adapter, send endpoint, alternate renderer, public registry protocol, metadata API, or configuration surface in v0.1. Development preview consumes the same registry and renderer.

API review result:

- Names are Vue/Nuxt-native and consistently E-prefixed; React shorthand props are absent from the typed API and have no shorthand behavior.
- Defaults are explicit where meaningful: `EHtml` uses `dir="ltr"` and `lang="en"`, `EHeading` defaults to `h1`, and `ELink`/`EButton` default to `target="_blank"`.
- Required destinations and image accessibility fields fail early; invalid document roots, unsafe content-replacement/event attributes, unknown templates, duplicate template names, discovery failures, and rendering failures are covered by actionable errors.
- `UnknownEmailTemplateError` reports the requested name and sorted known names. `EmailRenderError` identifies the template and preserves the original cause.
- Types and runtime rendering are generated from one server registry. The API is not auto-imported into client code, and production bundle assertions cover renderer/template client exclusion and development-preview exclusion.

No concrete API issue found in this review requires an immediate post-v0.1 breaking change. Any later provider, metadata, Tailwind, configuration, or registry proposal must pass its documented decision gate.

## Supported and unsupported surface

Supported primitives are the fourteen E-prefixed components listed in the frozen contract. Conformance also covers complete document rendering and plain-text conversion, including nested lists, ordered-list starts, blockquotes, hard breaks, tables, preformatted text, links, Unicode, preview exclusion, and Outlook-safe button text.

The following React Email components are explicitly unsupported in v0.1:

| React Email component | v0.1 decision |
| --- | --- |
| `CodeBlock` | Syntax-highlighted code output is outside the focused primitive set. |
| `CodeInline` | Inline code styling is outside the focused primitive set. |
| `Font` | Font-loading behavior requires separate email-client evidence. |
| `Markdown` | Markdown parsing is not required for native Vue SFC authoring. |
| `Tailwind` | Deferred until its post-v0.1 entry gate passes. |

This is not a claim of global or percentage compatibility. The exact six intentional divergences—`html-defaults`, four preview cases, and `row-columns`—and their Vue/email-safety reasons live only in the generated [conformance report](../conformance/report.md). Closely translated MIT algorithms and release notice requirements are recorded in [provenance](../conformance/provenance.md).
