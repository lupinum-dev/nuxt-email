Nuxt Email installs into an existing, supported Nuxt 4 application. Its email discovery and rendering conventions require no configuration.

## 1. Add the Nuxt module

```bash
pnpm add @lupinum/nuxt-email@next
```

::card{title="Use the scoped name" icon="lucide:info"}
The unscoped `nuxt-email` package on npm is unrelated to this project. Always install and import `@lupinum/nuxt-email`.
::

Register the unversioned package name in Nuxt configuration:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@lupinum/nuxt-email'],
})
```

### Set up a coding agent

The package ships its documentation for coding agents such as Claude Code,
Codex and Cursor, so they read pages that match the installed version. Give
your coding agent this task:

```text
Set up @lupinum/nuxt-email for coding agents as described under "Agent setup" in its README.
```

The steps are in the [README's Agent setup section](https://github.com/lupinum-dev/nuxt-email#agent-setup).

## 2. Confirm the TypeScript entry point

If your app does not already have one, add the ordinary Nuxt `tsconfig.json`:

```json [tsconfig.json]
{
  "extends": "./.nuxt/tsconfig.json"
}
```

## Optional code blocks

Syntax highlighting is opt-in. Nuxt Email uses the Shiki syntax highlighter, which you install in your application:

```bash
pnpm add @shikijs/core @shikijs/engine-javascript @shikijs/langs @shikijs/themes
```

Then configure exactly the languages your templates use and one theme:

```ts
export default defineNuxtConfig({
  modules: ['@lupinum/nuxt-email'],
  nuxtEmail: {
    codeBlock: {
      languages: ['typescript'],
      theme: 'github-dark',
    },
  },
})
```

Without `codeBlock`, `ECodeBlock` is not registered. Shiki is not loaded during module setup or included in the production server bundle.

The Shiki packages are optional peer dependencies, so an application that does not set `codeBlock` does not install them. If `codeBlock` is set and the packages are missing, module setup fails with the install instruction. Discovery directories, the preview route, and the render API remain fixed. See the [module behavior reference]($docs/reference/module) for the full contract.

## What the module registers

- Server-only components for the 14 built-in `E*` components, plus `ECodeBlock` when configured.
- A Nitro-only `renderEmail(name, props)` auto-import, typed from `app/emails/`.
- A build step that converts the Tailwind classes in `app/emails/` to inline styles.
- A development-only preview application at `/__email` (never present in production output).
