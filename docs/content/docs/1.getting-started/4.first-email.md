Every `.vue` file under `app/emails/` is an email template. Nested paths become slash-separated names; `app/emails/account/reset-password.vue` is named `account/reset-password`. The `app/emails/components/` folder is reserved for your own supporting components and is not discovered as a template.

## Write the template

::card{title="One EEmail root" icon="lucide:alert-triangle"}
A template renders exactly one `EEmail`, and `EEmail` is its root. A template without `EEmail`, with two, or with an element around it fails with `EmailRenderError`.
::

```vue [app/emails/welcome.vue]
<script setup lang="ts">
defineProps<{ name: string, actionUrl: string }>()
</script>

<template>
  <EEmail :subject="`Welcome, ${name}`" lang="en" preview="Your account is ready." class="bg-slate-100 p-6">
    <EContainer class="rounded-lg bg-white p-8">
      <EHeading class="text-2xl font-semibold text-slate-900">Welcome, {{ name }}</EHeading>
      <EText class="text-slate-600">Your account is ready.</EText>
      <EButton :href="actionUrl" class="rounded-md bg-emerald-600 px-5 py-3 text-white">Open dashboard</EButton>
    </EContainer>
  </EEmail>
</template>
```

`EEmail` sets the subject, the language, and the hidden inbox preview text. Its `class` and `style` apply to the email body. See [Structure]($docs/components/structure#eemail) for all props and the `head` slot.

You do not import the `E*` components. The module registers 14 built-ins and adds `ECodeBlock` when configured. Use normal `defineProps()`, slots, `v-if`, `v-for`, Tailwind v4 classes, HTML attributes, and Vue style bindings. The build converts the Tailwind classes to inline styles. See [Using Tailwind]($docs/guides/tailwind).

## Standalone renderer boundary

Email templates are `.vue` files that the module compiles with its own email compiler, separate from the application's Vue build. Each render uses a fresh Vue server-side rendering (SSR) application. Vue compiler macros such as `defineProps`, `defineOptions`, and `defineSlots` remain available without imports. Import other Vue APIs explicitly:

```vue
<script setup lang="ts">
import { computed } from 'vue'

const props = defineProps<{ name: string }>()
const greeting = computed(() => `Welcome, ${props.name}`)
</script>
```

Nuxt app auto-imports and host application context are not part of the email-rendering contract. Do not rely on these features inside a template:

- bare APIs such as `ref`;
- `useNuxtApp` or context-dependent composables;
- application plugins; or
- app-level provides.

Pass application data through typed props. Import standalone utilities explicitly. This boundary keeps output deterministic and lets the package testing helper use the same component.

## Add a preview fixture

To see the template in the [development preview]($docs/guides/preview-workflow), add one exact sibling `.fixtures.ts` file with deterministic sample props:

```ts [app/emails/welcome.fixtures.ts]
import type { EmailComponentProps } from '@lupinum/nuxt-email'
import type WelcomeEmail from './welcome.vue'

export default {
  name: 'Ada',
  actionUrl: 'https://example.com/dashboard',
} satisfies EmailComponentProps<typeof WelcomeEmail>
```

The file must default-export one object, and only the exact `.fixtures.ts` suffix is recognized. The `satisfies` expression makes fixture values obey the same prop type used by the generated render API. Fixtures are excluded from production builds — never import them into production code.

Next, [open the development preview]($docs/guides/preview-workflow) and inspect the fixture.
