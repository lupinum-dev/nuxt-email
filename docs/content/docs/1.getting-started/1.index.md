Nuxt Email is typed transactional email for Nuxt, with email-safe Tailwind v4. You write Vue single-file components (`.vue` files) in `app/emails/`. The module discovers them, generates typed Nitro render calls, and converts Tailwind classes to inline styles at build time.

It does one job and stops there. Nuxt Email does not send mail, choose providers, or manage recipients. You hand the rendered `html`, `text`, and `subject` to your provider SDK.

## Where it fits

Choose Nuxt Email when transactional messages belong to a Nuxt application and should share its Vue authoring model, TypeScript contracts, and Nitro deployment. The generated `renderEmail('welcome', props)` call is the product: no sidecar renderer, separate registry, or module configuration.

Nuxt Email is one focused option among Vue, Nuxt, standalone, and React email tools. [Compare the product boundaries]($docs/getting-started/choose-a-tool) before installing it.

## Why the output is trustworthy

Email HTML is unforgiving: clients strip `<style>`, break flexbox, and mangle padding. Nuxt Email combines conservative primitives with reproducible checks while keeping live-client claims separate.

- **Adapted from React Email.** The Tailwind-to-inline-style conversion and several components adapt algorithms from [React Email](https://react.email). Golden files in the repository pin the rendered output. They are regression evidence, not a universal inbox-rendering guarantee.
- **Tailwind v4 for email.** The build inlines compatible classes, preserves author-style precedence, and moves media-query and pseudo-class rules into the head. A production render loads neither Tailwind nor a CSS parser.
- **Deterministic.** Two renders of the same template and props return byte-identical HTML and a matching plain-text fallback. No IDs, timestamps, hydration payload, or mutable renderer state.
- **Server-only and typed.** `renderEmail('welcome', props)` is generated from your `app/emails/` folder. Unknown template names, missing props, and wrong types fail the type check (`vue-tsc`). At run time, a render rejects an unknown template name and missing or unknown props. It does not check the types of prop values.
- **Limits are documented.** No global "React Email compatible" claim exists. The [Tailwind limits]($docs/guides/tailwind#limits) and the [migration guide]($docs/reference/migration) record the differences.

## Supported environment

- **Node.js** `^22.22.3 || ^24.15.0 || ^26.0.0` — the supported even-numbered Node 22, 24, and 26 lines. The minimum versions are those of Nuxt 4.6. A newer Node.js major is outside the range of this package.
- **Nuxt** `>=4.5.1 <5`.
- **Vue** `^3.5.40`.

Nuxt `4.5.1` and Vue `3.5.40` are the compatibility baseline. Release consumers verify that minimum and the current compatible Nuxt 4 and Vue 3 versions without a dependency shim. CI covers Node 22, 24, and 26. Other Node majors, Nuxt 3, Nuxt 5, edge runtimes, and client-side email rendering are outside the support contract.

The Node range follows the supported even-numbered Node release lines that can run the Nuxt baseline. Keeping that range narrow lets the renderer use the platform Nuxt already requires and avoids compatibility code for old or short-lived Node releases.
