title: Module behavior

Nuxt Email is a standard Nuxt module registered in `modules`. Discovery, preview routes, and the render API are fixed by convention. Syntax-highlighted blocks are the one opt-in feature.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@lupinum/nuxt-email'],
})
```

## What the module registers

- **Components.** 14 built-in `E*` components are registered for use inside email templates. Configuring `codeBlock` adds `ECodeBlock`.
- **Build-time Tailwind.** The build converts the Tailwind classes of every file a template imports to inline styles and `<head>` rules. See [Using Tailwind]($docs/guides/tailwind).
- **`renderEmail`** — a Nitro-only auto-import generated from the discovered templates, typed with each template's name and props.
- **Development preview** — the `/__email` application and its endpoints, registered only when `nuxt.options.dev` is true.
- **Nuxt DevTools shortcut** — a development-only iframe tab pointing to that same baseURL-aware preview.

## Package entry points

The published package exposes six entry points. Runtime and type-only exports are listed separately.

| Import | Runtime exports | Type-only exports |
| --- | --- | --- |
| `@lupinum/nuxt-email` | Default Nuxt module | `ModuleOptions`, `RenderedEmail`, `EmailComponentProps` |
| `@lupinum/nuxt-email/build` | `buildEmailRegistry` (Node build only) | `BuildEmailRegistryOptions` |
| `@lupinum/nuxt-email/render` | `createEmailRenderer`, `EmailRenderError`, `UnknownEmailTemplateError` | `RenderedEmail`, `EmailComponentProps`, `EmailRenderArgs`, `EmailComponents` |
| `@lupinum/nuxt-email/testing` | `createTestRenderer`, `EmailRenderError`, `UnknownEmailTemplateError` | `RenderedEmail`, `CreateTestRendererOptions`, `TestRenderer`, `EmailTemplatePropsMap` |
| `@lupinum/nuxt-email/errors` | `EmailRenderError`, `UnknownEmailTemplateError` | — |
| `@lupinum/nuxt-email/agent-docs` | Packaged documentation for coding agents (Markdown files) | — |

The registry that `@lupinum/nuxt-email/build` generates imports `@lupinum/nuxt-email/render`. Application code does not call `createEmailRenderer` directly. After `nuxt prepare`, the generated `#nuxt-email/registry` alias exports the `EmailTemplateProps` type for [typed tests]($docs/guides/testing-your-emails#type-names-and-props).

There is no public `renderEmail` package export; its type is generated from each application's templates.
For a server registry without Nitro, see [Render outside Nitro]($docs/guides/standalone-rendering).

## Template discovery

- Templates are `.vue` files under `app/emails/`.
- Nested paths become slash-separated names (`app/emails/account/reset-password.vue` → `account/reset-password`).
- `app/emails/components/` is reserved for your own supporting components and is not discovered.
- Discovery follows the active Nuxt `srcDir`: a custom `srcDir: 'src/'` uses `src/emails/`.
- Email templates from inherited Nuxt layers are not merged into the active application's registry. Keep the application-owned templates in its active `srcDir/emails` tree.
- In a monorepo, register the module in each Nuxt application that sends email. Each application owns one registry from its own active `srcDir/emails`; package and layer templates are not merged implicitly.
- An optional `tailwind.css` in the email directory adds `@theme` and `@utility` blocks for every email.
- Sibling `.fixtures.ts` files supply deterministic preview props in development and are excluded from production output.

The registry is regenerated when templates are added, renamed, or deleted, which changes the generated server types. `nuxt dev` updates the types itself; outside `nuxt dev`, run `nuxt prepare` after such changes.

## Optional syntax highlighting

`codeBlock` is the only module option. It uses the Shiki syntax highlighter, which the application [installs itself]($docs/getting-started/installation#optional-code-blocks). The option requires one theme and a non-empty, closed language allowlist:

| Option | Type | Default | Required |
| --- | --- | --- | --- |
| `codeBlock` | `{ languages: readonly string[], theme: string }` | — | No |
| `codeBlock.languages` | Non-empty `readonly string[]` | — | Yes when `codeBlock` is set |
| `codeBlock.theme` | `string` | — | Yes when `codeBlock` is set |

```ts
export default defineNuxtConfig({
  modules: ['@lupinum/nuxt-email'],
  nuxtEmail: {
    codeBlock: {
      languages: ['typescript', 'vue'],
      theme: 'github-dark',
    },
  },
})
```

Only the configured languages and the grammars they import enter the server bundle. Nuxt Email creates the highlighter on first use. Without this option, `ECodeBlock` is unregistered and Shiki performs no module-setup or production-bundle work. The Shiki packages are optional peer dependencies; setup fails with the install instruction when `codeBlock` is set and they are missing. Unsupported top-level options fail during setup.

## Production boundary

The production server keeps templates referenced by its registry because Nitro renders them there. The client bundle excludes those templates.

The `/__email` application, its endpoints, and every discovered `.fixtures.ts` module are absent from production output. See the [preview workflow]($docs/guides/preview-workflow) and [security boundary]($docs/reference/render-email#security-boundary).
