title: Using Tailwind
description: How ETailwind inlines utilities, how nested-component classes are reached, and the exact documented limitations.
---

Wrap an email document in `<ETailwind>` and Tailwind v4 utility classes on descendant elements are compiled into email-safe output at render time. Compatible declarations become inline styles; the boundary is server-only and requires a `<head>` inside it.

```vue
<ETailwind>
  <EHtml lang="en">
    <EHead />
    <EBody class="bg-gray-100">
      <EContainer class="p-4">
        <EText class="text-red-500">Styled with Tailwind</EText>
      </EContainer>
    </EBody>
  </EHtml>
</ETailwind>
```

## Precedence and non-inlinable rules

Inlining precedence is **component defaults < Tailwind utilities < author `style`**. Media queries and pseudo-classes cannot become inline styles. Nuxt Email moves them to a `<style>` element in `<head>`. It sanitizes residual class names and preserves Outlook-specific (`mso-*`) properties. Rendering fails with the affected class names when these rules have no head inside the boundary.

Tailwind v4 emits nested CSS for variants such as `hover:` and responsive combinations. Nuxt Email recursively flattens that nesting and converts media range syntax before it places the CSS in the email. A Tailwind nesting shape that cannot be converted safely fails the render instead of leaving a raw `&` rule in the output.

## Dark mode

Keep the base colors readable on their own. Some email clients ignore dark-mode rules, and others transform colors without using your rules.

The `dark:` variant emits `@media (prefers-color-scheme: dark)` CSS in `<head>`. Treat it as progressive enhancement.

```vue
<EBody class="bg-white text-slate-900 dark:bg-slate-900 dark:text-white">
  <EText>Readable with or without dark-mode support.</EText>
</EBody>
```

Support varies across Gmail and Outlook versions. Check the current [Can I Email evidence for `prefers-color-scheme`](https://www.caniemail.com/features/css-at-media-prefers-color-scheme/) and test the clients your recipients use.

You can extend the engine through props:

- `config` — a Tailwind config (everything except `content`), matching React Email's `TailwindConfig`.
- `theme` — raw CSS appended to the `@theme` layer.
- `utility` — raw CSS appended to the utilities layer.

## Share tokens, not the Nuxt stylesheet

Email rendering does not load the Nuxt application's CSS bundle, and browser CSS variables cannot be relied on in email clients. A class such as `text-primary` must resolve to a concrete value while the email renders.

Keep one application-owned token source and feed its value into `ETailwind` explicitly:

```vue
<script setup lang="ts">
import { emailTheme } from '~/shared/email-theme'
</script>

<template>
  <ETailwind :theme="emailTheme">
    <EHtml lang="en">
      <EHead />
      <EBody>
        <EText class="text-primary">Concrete email color</EText>
      </EBody>
    </EHtml>
  </ETailwind>
</template>
```

```ts [shared/email-theme.ts]
export const emailTheme = '@theme { --color-primary: #2563eb; }'
```

The same token module can generate or inform your Nuxt theme, but Nuxt Email does not add a second CSS discovery path or silently import application styles.

`ETailwind` accepts the `config`, `theme`, and `utility` values you pass directly. It does not resolve arbitrary CSS file imports or CSS `@plugin` module imports at render time; supply executable Tailwind plugins through `config`. This keeps production rendering independent of the application filesystem.

## Classes inside nested components

Classes written directly in the email template are resolved during rendering. Classes emitted inside a nested component are resolved too. A reusable card or button therefore uses the same Tailwind behavior as inline markup:

```vue [Card.vue]
<template>
  <div class="bg-red-500 p-4 md:text-lg">
    <EText class="m-0">Title</EText>
    <EButton class="bg-blue-600 px-4 py-2" href="https://example.com">Open</EButton>
  </div>
</template>
```

```vue [email template]
<ETailwind>
  <EHtml lang="en">
    <EHead />
    <EBody>
      <Card />
    </EBody>
  </EHtml>
</ETailwind>
```

Style-bearing primitives such as `EText` and `EButton` resolve their Tailwind classes before their email-specific layout work. Plain HTML and structural components such as `EHtml` are handled in a second pass over the rendered HTML. That pass changes only marked class targets. Outlook-specific conditional comments and every other byte stay unchanged.

Rules that cannot be inlined, such as `md:text-lg`, still reach the `<head>` style element. Rendering fails if those rules have no head inside the boundary.

## Documented limitations

::card{title="Limitations" icon="lucide:alert-triangle"}
- `ECodeInline`, `EMarkdown`, `EPreview`, and `EFont` do **not** treat a nested `class` as a Tailwind style target — their `class`/head semantics differ.
- Nested `<ETailwind>` boundaries are **not** a supported configuration.
- Arbitrary CSS imports and CSS `@plugin` module imports are **not** resolved during rendering; executable plugins belong in `config`.
- Responsive or pseudo-class padding on `EContainer`, `ESection`, or `ERow` remains a CSS rule on the table; use an inner `EColumn` when that padding must survive clients that force collapsed table borders.
- Animation utilities include only the keyframes used by that render. Treat animation as best-effort progressive enhancement: [estimated email-client animation support is limited](https://www.caniemail.com/features/css-animation/), so the message must remain understandable when animation does not run.
- CSS nesting is downleveled because [estimated native nesting support in email clients is low](https://www.caniemail.com/features/css-nesting/). No raw nesting is intentionally emitted.
- Output tracks the fixed Tailwind version compiled by the engine.
::

Emails without `<ETailwind>` do not run the Tailwind path. The conformance cases cover basic inlining, media queries, Outlook-specific properties, nested components, and residual class sanitization. See the [conformance report]($docs/reference/conformance).
