Put Tailwind v4 classes on any element or component in a template. No wrapper component is needed.

```vue [app/emails/welcome.vue]
<template>
  <EEmail subject="Welcome" lang="en" class="bg-slate-100">
    <EContainer class="p-4">
      <EText class="text-red-500 sm:text-lg">Styled with Tailwind</EText>
    </EContainer>
  </EEmail>
</template>
```

The build reads the classes from every file a template imports and computes their styles once. A production render looks the styles up in that table. It loads neither Tailwind nor a CSS parser.

The build writes sizes in `px`, at 16 px per `rem`, because Outlook on Windows does not support `rem`. For example, `p-4` becomes `padding:16px`. Colors are written as hex or `rgba()` instead of `oklch()`. For example, `text-gray-700` becomes `color:#364153`.

## What is inlined and what goes to `<style>`

- A class with plain declarations, such as `text-red-500`, becomes an inline `style` on the element. The class is removed from `class`.
- A class with a media query or a pseudo-class, such as `sm:text-lg` or `hover:underline`, cannot become an inline style. Nuxt Email keeps a sanitized class name on the element and writes the rule into a `<style>` element in `<head>`.
- A render writes only the `<head>` rules of the classes it used. Animation utilities add only the keyframes they reference.

Inlining precedence is **component defaults < Tailwind classes < author `style`**. Tailwind declarations apply in Tailwind's stylesheet order, as in a browser, whatever the order in `class`: `pl-2 p-4` and `p-4 pl-2` both give `padding:16px;padding-left:8px`. Author `style` declarations come last, so an author shorthand such as `padding` also beats a Tailwind longhand such as `padding-left`. Outlook-specific (`mso-*`) properties stay unchanged. The `<head>` rules go before the first `<style>` from the `head` slot, so author CSS comes last.

Tailwind v4 emits nested CSS for variants such as `hover:` and responsive combinations. The build flattens that nesting with [Lightning CSS](https://lightningcss.dev) and converts media range syntax, because [estimated native nesting support in email clients is low](https://www.caniemail.com/features/css-nesting/). A class inside an at-rule other than `@media` or `@supports` fails the build.

## Dark mode

Keep the base colors readable on their own. Some email clients ignore dark-mode rules, and others transform colors without using your rules.

The `dark:` variant emits `@media (prefers-color-scheme: dark)` CSS in `<head>`. Treat it as progressive enhancement.

```vue
<EEmail subject="Welcome" lang="en" class="bg-white text-slate-900 dark:bg-slate-900 dark:text-white">
  <EText>Readable with or without dark-mode support.</EText>
</EEmail>
```

Support varies across Gmail and Outlook versions. Check the current [Can I Email evidence for `prefers-color-scheme`](https://www.caniemail.com/features/css-at-media-prefers-color-scheme/) and test the clients your recipients use.

## Add theme tokens and utilities

Create `app/emails/tailwind.css` to customize Tailwind for every email. Use `@theme` for tokens and `@utility` for your own utilities:

```css [app/emails/tailwind.css]
@theme {
  --color-brand: #00dc82;
}

@utility card {
  border-radius: 8px;
  padding: 24px;
}
```

A template can then use `bg-brand` and `card`. The file is optional. Email rendering does not load the Nuxt application's CSS bundle, so a token must have a concrete value in this file.

## Add class names that are not in the source

The build finds a class only when its full name is in a file that a template imports. When a template builds a name at run time, list the possible names in `app/emails/tailwind.css` with Tailwind's `@source inline()`:

```css [app/emails/tailwind.css]
@source inline("text-{red,amber,emerald}-600");
```

```vue [app/emails/status.vue]
<EText :class="`text-${tone}-600`">Status</EText>
```

Tailwind expands the braces, so this example adds three classes. The build computes the styles of every listed class, and an email gets only the styles of the classes that it uses. List only the names that a render can use.

A class from a plain CSS rule in `tailwind.css`, such as `.footer-link:hover { color: #00dc82 }`, needs no `@source inline()`. The build knows every class that this file defines.

`@source` with a path fails the build. The build already reads every file that a template imports.

## Classes inside your own components

Components that a template imports use the same Tailwind behavior as the template:

```vue [app/emails/components/Card.vue]
<template>
  <div class="bg-white p-4 md:text-lg">
    <EText class="m-0">Title</EText>
    <EButton class="bg-blue-600 px-4 py-2" href="https://example.com">Open</EButton>
  </div>
</template>
```

Import the component explicitly in the template. In the module and in `createTestRenderer()`, the component can also live elsewhere in the project, for example in `app/components/`. The build follows the import and reads that file's classes. Files in `node_modules` are not read, including workspace packages linked there.

During development, the module rebuilds the emails when Nuxt's file watcher reports a change to an imported file. Nuxt watches files in the project, so a change to a file in `node_modules` does not trigger a rebuild.

## Limits

::card{title="Limits" icon="lucide:alert-triangle"}
- **Write every class completely in source.** The build reads the source text. It cannot resolve a class name that is built at run time, such as `` `bg-${color}-500` ``. Write the full names, for example in a ternary or an object: `:class="{ 'bg-red-500': urgent }"`. For a larger set of names, use [`@source inline()`](#add-class-names-that-are-not-in-the-source).
- **Write classes in `class` or `:class`.** A class inside a `v-bind` object, such as `v-bind="{ class: 'p-4' }"`, is not resolved and stays in `class` unchanged.
- **The build reads only imported files.** A file that no template imports does not contribute classes. Files in `node_modules` are not read.
- **Unknown classes stay in `class`.** A class that Tailwind does not know stays in the `class` attribute unchanged. The [development preview]($docs/guides/preview-workflow) lists these classes under "Classes kept as written", and [`createTestRenderer()`]($docs/guides/testing-your-emails#classes-without-effect-fail-the-test) fails on them.
- **JavaScript config and plugins are not supported.** `@config`, `@plugin`, and other module imports in `app/emails/tailwind.css` fail the build. Use `@theme` and `@utility` instead.
- **Container queries are not supported.** `@container` and `@sm:` classes fail the build.
- **Responsive padding on table layout components works for padding-only classes.** `EEmail`, `EContainer`, `ESection`, and `ERow` move a class such as `sm:p-8` or `md:px-10` to their inner cell, where the padding applies. A class whose rule also sets other properties stays on the table, where its padding has no effect.
- **Some utilities are not email-safe today.** Their output still contains syntax that some email clients do not support: `bg-linear-to-r` (`var()`), `group-hover:` variants (`:where()` or `:is()` inside the selector), and an arbitrary value with `calc()`, such as `w-[calc(100%-2rem)]`. Check them in your target clients or use another utility.
- **Generated CSS is left-to-right.** Logical utilities such as `ps-4`, `me-2`, `text-start` and `rounded-s-lg` become their left-to-right physical properties (`padding-left`, `margin-right`, `text-align:left`, `border-top-left-radius`), because email clients read logical properties poorly. In a right-to-left email, use physical utilities such as `pr-4` and `text-right`.
- **Utilities that only change another class do nothing on their own.** A class such as `ring-blue-500` sets only a custom property that another utility, here `ring-2`, reads. The build resolves custom properties per class, so it does not combine the two: use one utility that sets the final value, or an arbitrary value. Such classes stay in `class`, and the development preview lists them under "Classes kept as written".
- **Treat animation as progressive enhancement.** [Estimated email-client animation support is limited](https://www.caniemail.com/features/css-animation/), so the message must remain understandable when animation does not run.
- **Output tracks the Tailwind version the package depends on.**
::
