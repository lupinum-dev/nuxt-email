---
title: Testing your emails
description: Compile your email directory and assert on rendered output in unit tests with createTestRenderer.
---

`createTestRenderer` from `@lupinum/nuxt-email/testing` compiles your email directory with the same compiler as the module. It returns a `renderEmail` function. It does not start Nuxt.

```ts [test/welcome.test.ts]
import { createTestRenderer } from '@lupinum/nuxt-email/testing'
import { expect, test } from 'vitest'

test('welcome renders the recipient name', async () => {
  const { renderEmail } = await createTestRenderer({ rootDir: process.cwd() })
  const { html, text, subject } = await renderEmail('welcome', {
    name: 'Ada',
    actionUrl: 'https://example.com/dashboard',
  })

  expect(subject).toBe('Welcome, Ada')
  expect(html).toContain('Welcome, Ada')
  expect(text).toContain('https://example.com/dashboard')
})
```

The helper applies the same template rules and Tailwind output as the module. It does not load Nuxt configuration. It resolves Nuxt's default aliases: `~` and `@` point to the parent of the email directory (`app/` for `app/emails`, `src/` for `src/emails`), and `~~` and `@@` point to `rootDir`. A template can import `~/components/EmailFooter.vue` as it does in Nuxt. Custom aliases from `nuxt.config.ts` are not available.

The result is the same `RenderedEmail` shape that [`renderEmail`]($docs/reference/render-email) returns in Nitro: `html`, `text`, and `subject`. Rendering is deterministic, so the same template and props always produce the same output. No Vue plugin is needed in the test configuration. The helper is Node-only. Do not import it from application components, shared browser code, or client plugins.

## Options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `rootDir` | `string` | — | The application root. The helper does not load Nuxt configuration. |
| `templatesDir` | `string` | `app/emails` | The email directory, relative to `rootDir`. |
| `codeBlock` | `CodeBlockOptions` | — | The `codeBlock` option of the module, when templates use `ECodeBlock`. |

Share one `codeBlock` value between `nuxt.config.ts` and the tests with the exported type:

```ts [test/code-block.ts]
import type { CodeBlockOptions } from '@lupinum/nuxt-email/testing'

export const codeBlock: CodeBlockOptions = { languages: ['typescript'], theme: 'github-dark' }
```

## Type names and props

Pass the generated `EmailTemplateProps` type to check template names and props in the test. Run `nuxt prepare` first so that `#nuxt-email/registry` exists:

```ts [test/welcome.test.ts]
import type { EmailTemplateProps } from '#nuxt-email/registry'
import { createTestRenderer } from '@lupinum/nuxt-email/testing'

const { renderEmail } = await createTestRenderer<EmailTemplateProps>({ rootDir: process.cwd() })
```

Without the type argument, `renderEmail` accepts any name and props object. A wrong name or invalid props still fail at run time.

## Test templates with ECodeBlock

Pass the same `codeBlock` option that `nuxt.config.ts` gives the module:

```ts
const { renderEmail } = await createTestRenderer({
  rootDir: process.cwd(),
  codeBlock: { languages: ['typescript'], theme: 'github-dark' },
})
```

Without the option, `createTestRenderer` fails when a template uses `ECodeBlock`.

## Each call compiles again

`createTestRenderer` has no cache. Each call compiles the whole email directory. Call it once per test file, for example at the top level or in `beforeAll`, and reuse `renderEmail` across tests.

Prefer focused assertions on recipient-visible text, links, required attributes, and client-specific markup. Whole-document snapshots can approve accidental output.

## What testing does not replace

Unit tests prove your template's structure and content are stable and deterministic. They do **not** prove how a real client renders the message. Pair them with the [manual client compatibility]($docs/guides/client-compatibility) checklist before a release.
