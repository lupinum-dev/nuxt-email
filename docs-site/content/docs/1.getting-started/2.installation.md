title: Installation
description: Add nuxt-email to a supported Nuxt application, register the module, and confirm there are no module options.
---

Nuxt Email installs into an existing, supported Nuxt 4 application. It ships as a standard Nuxt module with no configuration surface.

## 1. Install the package

`0.1.0` is a release candidate. Install the exact candidate tarball identified in the release record rather than assuming a registry package of the same name exists:

```bash
pnpm add /absolute/path/to/nuxt-email-0.1.0-rc.tgz
```

::card{title="Why the tarball?" icon="lucide:info"}
The `nuxt-email` npm name is not yet confirmed as owned or published. Using the recorded tarball and its SHA-256 guarantees you install the audited artifact.
::

## 2. Register the module

```ts [nuxt.config.ts]
import NuxtEmail from 'nuxt-email'

export default defineNuxtConfig({
  modules: [NuxtEmail],
})
```

## 3. Confirm the TypeScript entry point

If your app does not already have one, add the ordinary Nuxt `tsconfig.json`:

```json [tsconfig.json]
{
  "extends": "./.nuxt/tsconfig.json"
}
```

## Zero module options

Nuxt Email accepts **no** module options in v0.1. Passing any option throws during setup with a `TypeError` naming the received keys:

```ts
// This throws: "nuxt-email does not accept module options; received: foo"
modules: [[NuxtEmail, { foo: true }]]
```

Discovery directories, the preview route, and the render API are fixed by convention, not configured. See the [module behavior reference]($docs/reference/module) for the full contract.

## What the module registers

- Auto-registration of the nineteen `E*` components inside the isolated email renderer.
- A Nitro-only `renderEmail(name, props)` auto-import, typed from `app/emails/`.
- A Nitro-only `defineEmail(options)` auto-import for declaring a subject.
- A development-only preview application at `/__email` (never present in production output).
