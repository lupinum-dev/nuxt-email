title: Testing your emails
description: Render templates and assert on their output in unit tests with the nuxt-email/testing utilities.
---

Nuxt Email exposes first-class testing utilities from the `nuxt-email/testing` subpath. They let you render an email component and assert on its HTML and plain text in a unit test **without booting a Nuxt app**.

```ts
import { renderEmailComponent, normalizeEmailHtml } from 'nuxt-email/testing'
```

## renderEmailComponent

Renders a Vue email component to `{ html, text, subject? }` — the same `RenderedEmail` shape [`renderEmail`]($docs/reference/render-email) returns, produced by the same renderer.

```ts [test/welcome.test.ts]
import { renderEmailComponent } from 'nuxt-email/testing'
import Welcome from '../app/emails/welcome.vue'

test('welcome renders the recipient name', async () => {
  const { html, text } = await renderEmailComponent(Welcome, {
    firstName: 'Ada',
    activationUrl: 'https://example.com/activate',
  })

  expect(html).toContain('Welcome, Ada')
  expect(text).toContain('Welcome, Ada')
})
```

`renderEmailComponent(component, props?)` takes the imported component and a props object and returns `Promise<RenderedEmail>`. Because rendering is deterministic, the same component and props always produce the same output.

## normalizeEmailHtml

`normalizeEmailHtml(html)` canonicalizes rendered email HTML so two structurally equivalent documents compare equal regardless of insignificant serialization differences. It is the exact normalizer nuxt-email uses for its own React Email conformance suite. It:

- strips framework boundary comment markers (`<!--$-->`, `<!--/$-->`, and the `<!--html-->` / `<!--head-->` / `<!--body-->` markers),
- sorts each element's attributes by name,
- drops a trailing `;` from `style` values and collapses `class` whitespace,
- normalizes self-closing tags to their open-tag form and lowercases the `cellPadding` / `cellSpacing` attribute names.

Use it for stable snapshots:

```ts
test('welcome matches its snapshot', async () => {
  const { html } = await renderEmailComponent(Welcome, {
    firstName: 'Ada',
    activationUrl: 'https://example.com/activate',
  })

  expect(normalizeEmailHtml(html)).toMatchSnapshot()
})
```

## Asserting on the subject

If a template declares a subject with [`defineEmail`]($docs/guides/subject-lines), `renderEmailComponent` computes it from the props you pass:

```ts
const { subject } = await renderEmailComponent(Welcome, { firstName: 'Ada', activationUrl: '…' })
expect(subject).toBe('Welcome aboard, Ada')
```

## What testing does not replace

Unit tests prove your template's structure and content are stable and deterministic. They do **not** prove how a real client renders the message. Pair them with the [manual client compatibility]($docs/guides/client-compatibility) checklist before a release.
