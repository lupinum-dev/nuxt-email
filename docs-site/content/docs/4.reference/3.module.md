---
title: Module behavior
description: What the module registers, the fixed conventions it follows, and the zero-options policy it enforces.
---

Nuxt Email is a standard Nuxt module registered in `modules`. Its behavior is fixed by convention, not configured.

```ts [nuxt.config.ts]
import NuxtEmail from '@lupinum/nuxt-email'

export default defineNuxtConfig({
  modules: [NuxtEmail],
})
```

## What the module registers

- **Components.** The eighteen `E*` components are auto-imported for use inside email templates. Templates do not import them.
- **`renderEmail`** — a Nitro-only auto-import generated from the discovered templates, typed with each template's name and props.
- **`defineEmail` entry point** — import it from `@lupinum/nuxt-email/define-email` inside a template to declare a [subject]($docs/guides/subject-lines).
- **Development preview** — the `/__email` application and its endpoints, registered only when `nuxt.options.dev` is true.

## Package entry points

The package keeps one small entry point per concern:

| Import | Purpose |
| --- | --- |
| `@lupinum/nuxt-email` | Register the Nuxt module. |
| `@lupinum/nuxt-email/define-email` | Declare a template subject and import its metadata errors. |
| `@lupinum/nuxt-email/testing` | Render imported components and normalize HTML in unit tests. |
| `@lupinum/nuxt-email/errors` | Import supported runtime errors. |

There is no public `renderEmail` package export; its type is generated from each application's templates.

## Template discovery

- Templates are `.vue` files under `app/emails/`.
- Nested paths become slash-separated names (`app/emails/account/reset-password.vue` → `account/reset-password`).
- `app/emails/components/` is reserved for your own supporting components and is not discovered.
- Sibling `.fixtures.ts` files supply deterministic preview props in development and are excluded from production output.

The registry is regenerated when templates are added, renamed, or deleted, which changes the generated server types. Run `nuxt prepare` after such changes.

## Zero module options

Nuxt Email accepts **no** options. The module throws during setup if any option is passed:

```ts
// Throws a TypeError: "nuxt-email does not accept module options; received: foo"
modules: [[NuxtEmail, { foo: true }]]
```

This is a deliberate design decision, not a missing feature. Discovery directories, the preview route, the render API name, and rendering behavior are all fixed so there is one correct configuration and no matrix of option-dependent behavior to reason about or support.

## Production boundary

In a production build the module keeps templates that the server registry references (the Nitro handler needs them) while excluding them from the client bundle. The `/__email` application, its endpoints, and every discovered `.fixtures.ts` module are absent from production output entirely. See the [preview workflow]($docs/guides/preview-workflow) and the [security boundary]($docs/reference/render-email#security-boundary).
